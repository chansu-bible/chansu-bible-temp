# 장면 성경 네이티브 앱 설계

2026-10-09. 설계 승인(같은 날, "좋아 진행해줘"). 사용자 결정: 앱은 React Native(Expo)로 만들고, 로그인은 키클락을 쓰며, 개발 단계의 키클락·서버·DB는 로컬 도커로 띄운다. 기능 목업 15장(아티팩트 "장면 성경 앱 기능 목업", https://claude.ai/artifact/3yVxS9ceCVoM2qUmSW12aS)을 전부 앱에 넣고, 목업에서 정하지 않았거나 고쳐야 할 세부는 만들면서 정한다(이 문서 6절에 적는다).

## 1. 목표와 완료 기준

안드로이드와 iOS에서 같은 코드로 도는 읽기 앱을 만든다. 웹 목업(`app/`)의 읽기 경험을 그대로 옮기고, 목업 5~15번 기능을 더한다.

- 묶음(본문, 장면, 그림, 낭독, 설정집)은 앱 안에 들어 있어 비행기 모드에서도 읽힌다.
- 로그인하지 않아도 모든 읽기 기능과 기기 안 기록(진도, 계획, 밑줄, 메모)이 동작한다. 로그인하면 기록이 서버와 동기화되고 질문하기를 쓸 수 있다.
- 각 단계(3절)는 자기 완료 기준을 통과해야 끝난다. 화면은 Expo 웹으로 브라우저에서 확인하고, 계산과 저장은 자동 테스트로 확인한다. 네이티브 전용 기능(백그라운드 낭독, 위젯)은 기기 빌드에서 확인한다(9절).

## 2. 범위

**한다.** 목업 1~15번 전부, 키클락 로그인, 기록 동기화 서버, 질문하기 서버, 원어·퀴즈 콘텐츠를 만드는 파이프라인 단계와 그 검수.

**하지 않는다.** 앱 스토어 출시, 운영 서버 호스팅, 묶음 무선 갱신(OTA), 푸시 알림, 다른 사람과 나누는 소셜 기능, 결제. 창세기 11장 이후와 다른 책의 콘텐츠 제작(서재에는 "만드는 중", "예정"으로만 보인다).

## 3. 단계

한 번에 만들지 않고 다섯 단계로 나눈다. 단계마다 구현 계획(`docs/superpowers/plans/`)을 따로 쓰고, 끝나면 커밋한다.

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 1 | `reader-core` 분리, Expo 앱 껍데기, 읽기 화면·장면 그림·낱말 풀이·이름 연결·인물 카드·목차·연표·설정·지도·장소 전환 안내·해설 시트·기기 낭독 | 웹 목업과 같은 동작을 Expo 웹에서 확인. `reader-core` 테스트가 옮긴 뒤에도 전부 통과. 웹 목업도 `reader-core`를 쓰며 그대로 동작 |
| 2 | 기기 저장소, 읽기 계획과 진도(5), 가계도(6), 장면 카드 공유(7), 검색(8), 밑줄·메모·즐겨찾기(9) | 기록이 앱을 껐다 켜도 남음. 검색 색인이 묶음 빌드 때 만들어짐. 각 화면 Expo 웹 확인 |
| 3 | 도커(키클락, Postgres, 서버), 로그인, 기록 동기화 | 로컬 키클락으로 로그인·로그아웃. 두 기기(웹 창 둘)에서 메모가 서로 보임. 서버 테스트 통과 |
| 4 | 낭독 플레이어(10, 화면 꺼도 재생), 홈 화면 위젯(15) | 기기 빌드에서 잠금 화면 재생과 위젯 표시 확인(9절의 빌드 환경이 필요) |
| 5 | 원어와 출처(11), 이해 확인 퀴즈(12), 질문하기(13), 서재(14) | 원어·퀴즈가 검수를 거쳐 묶음에 들어감. 질문하기가 근거 장절을 붙여 답하고, 자료에 없으면 없다고 답함 |

**진행.** 1단계 구현 완료(2026-10-09, 계획 `docs/superpowers/plans/2026-10-09-mobile-phase1-reader.md`). Expo 웹에서 읽기·스크롤·낱말·카드·목차·연표·설정·장 고르기·장면 밀기·장소 전환 지도·낭독을 확인했다. 1단계는 Expo Go에 든 모듈만 써서 폰의 Expo Go로 바로 볼 수 있다. 만들면서 바꾼 것: 장면은 그림을 좌우로 밀어 넘긴다(아래 버튼은 두지 않음). 글자 크기는 슬라이더 대신 다섯 단계 단추다. 글자 크기를 바꾸면 본문을 새로 그려 읽던 절을 지킨다. 본문 머리의 "창세기 N장"을 누르면 장 고르기 시트가 열린다.

2단계 구현 완료(2026-10-09, 계획 `docs/superpowers/plans/2026-10-09-mobile-phase2-home-notes-search.md`). 홈(오늘의 읽기, 연속 읽기, 이어 읽기, 계획과 장별 진도, 바로 가기), 절을 길게 눌러 여는 밑줄·메모·즐겨찾기와 장면 카드 공유, 내 메모, 검색, 인물 사전, 가계도를 Expo 웹에서 확인했다. 기록은 기기의 SQLite(웹은 localStorage)에 줄마다 수정 시각·지운 시각·미동기화 표시와 함께 둔다. 만들면서 바꾼 것: 검색 색인을 묶음에 넣지 않고 앱이 묶음을 바로 훑는다(창세기 1~10장 규모에서 충분히 빠르다). 밑줄 색은 목업대로 셋이다. 읽기 설정은 기기마다 달라 동기화하지 않는다. "N일째"는 읽은 장면의 날짜로 센 연속 읽기다. 계획에는 시작일을 두지 않는다(오늘 분량은 오늘 이전에 읽은 장면으로 정한다).

3단계 구현 완료(2026-10-09, 계획 `docs/superpowers/plans/2026-10-09-mobile-phase3-auth-sync.md`). 도커로 Postgres와 키클락을 띄우고, 동기화 서버(`server/`)와 앱의 로그인·동기화·계정 화면을 만들었다. Expo 웹에서 로그인 전 기록이 계정으로 올라가는 것, 다른 기기가 올린 메모를 받아 오는 것, 앱에서 지운 메모가 3초 뒤 서버에 지움으로 남는 것, 새로 고쳐도 로그인이 이어지는 것, 로그아웃하면 기기 기록이 비고 다시 로그인하면 돌아오는 것, 서버가 꺼졌을 때 로그아웃하면 못 올린 기록을 알리고 한 번 더 묻는 것을 확인했다. 만들면서 바꾼 것: 서버는 개발 중 호스트에서 돌리고 도커에는 Postgres와 키클락만 둔다. Drizzle 대신 SQL을 직접 쓴다(표가 하나다). 서버 시험은 도커 대신 PGlite(메모리 Postgres)로 돌린다. Expo 웹은 로그인 창을 팝업 대신 같은 창에서 연다(팝업을 막는 브라우저와 앱의 미리 보기 창에서도 되게). 로그인 창은 늘 로그인 양식을 보인다(로그아웃 뒤 다른 계정으로 들어갈 수 있게). 로그아웃하면 기기 기록을 지운다(기록은 계정에 남는다). 지운 기록은 내용을 비운다.

4단계 코드 완료, 기기 확인 전(2026-10-09, 계획 `docs/superpowers/plans/2026-10-09-mobile-phase4-player-widgets.md`). 장면 낭독 파일, 앱 전체 낭독 재생기(잠금 화면 정보, 백그라운드 재생, 잠자기 타이머, 속도, 자막, 다음에 들을 것, 들은 곳 기록), 낭독 플레이어와 홈의 작은 재생 막대, 홈 화면 위젯(안드로이드, iOS)을 만들었다. Expo 웹에서 플레이어(장면이 끝나면 다음 장면, 절 넘기기, 진행 막대, 속도, 자막, 장면 끝 타이머, 다음에 들을 것, 웹 Media Session의 장면 정보)와 읽기 화면이 낭독을 따라가는 것을 확인했다. `expo prebuild`로 네이티브 설정도 확인했다. 안드로이드는 녹음 권한 없음, 미디어 재생 포그라운드 서비스, 위젯 리시버와 4×2 설정, 쓰지 않는 권한 제거, 기기의 어두운 화면 따르기. iOS는 백그라운드 오디오, 마이크 설명 없음, 앱과 위젯의 App Group, 위젯 대상(iOS 프로젝트는 Windows에서 만들 수 없어 리눅스 컨테이너에서 만들었다). 잠금 화면 재생과 위젯 표시는 빌드 환경(9절)을 정한 뒤 기기에서 확인한다(11절). 만들면서 바꾼 것: 절 파일을 바꿔 가며 재생하지 않고 장면마다 절 낭독을 이은 파일 하나를 재생한다(화면이 꺼진 동안 파일을 바꾸는 일이 장면 경계에서만 생기고, 잠금 화면에 장면이 곡 하나로 보인다). 낭독은 앱 전체에 하나라 읽기 화면을 닫아도 이어지고, 들은 곳까지 읽기 위치와 읽은 장면이 적힌다. 잠자기 타이머는 끔·15·30·60분·장면 끝이고, 분 타이머는 그때 읽던 절을 마저 읽고 멈춘다. 잠금 화면의 앞뒤 단추는 10초 건너뛰기다(expo-audio가 곡 넘기기를 주지 않는다). iOS 위젯 그림은 앱이 App Group에 적어 준다(위젯 안에 그림을 넣으면 PNG로 바뀌어 11MB가 된다). 마이크 권한을 뺐다. iOS를 빌드할 때는 app.json에 `ios.appleTeamId`가 있어야 한다.

5단계 구현 완료, 승인 전(2026-10-09, 계획 `docs/superpowers/plans/2026-10-09-mobile-phase5-original-quiz-ask-library.md`). 파이프라인에 `original`(OSHB와 스트롱 사전을 고정된 커밋에서 받음), `original-gloss`(사전 항목마다 한국어 뜻 초안), `quiz`(장마다 4지선다 다섯, 검수 모델이 근거 절 확인) 단계를, 관리 도구에 "원어 뜻"·"퀴즈" 검수 화면을, 동기화 서버에 질문하기(`POST /ask`, 계정마다 하루 20번)를, 앱에 원어 보기·자료 출처·이해 확인 퀴즈·질문하기·서재를 더했다. 창세기 1~10장의 낱말 3,401개와 사전 항목 568개, 한국어 뜻 초안 568개, 문제 50개(검수 통과 49, 지적 1)를 만들었다(글 모델 비용 약 0.93달러). 승인된 것만 묶음에 넣는 길까지 만들었고, 승인은 사람이 관리 도구에서 할 일로 남았다. 승인 전에는 원어 보기에 "뜻 검수 중"과 영어 정의가 보이고 퀴즈는 열리지 않는다. Expo 웹에서 초안을 승인으로 친 임시 묶음(커밋하지 않음)으로 원어 시트(낱말 누르기, 나오는 곳에서 절로), 자료 출처, 퀴즈(맞음·틀림, 결과, 끝까지 풀면 quizDone이 계정에 올라감), 질문하기(로그인 안내, 제안 질문, 근거 표식으로 읽기 화면과 해설 시트 열기, 설정집 펼치기, "자료에 없어요"와 가까운 대목, 오늘 남은 질문), 서재를 확인했다. 만들면서 바꾼 것: 원어 보기는 낱말 풀이가 아니라 절에 붙이고 절을 길게 눌러 연 시트에서 연다. 히브리어 낱말은 오른쪽에서 왼쪽으로 늘어놓고 한국어 절 낱말과 짝짓지 않는다. 퀴즈는 승인된 문제가 셋 이상인 장만 열고, 장의 끝과 목차의 장 머리에서 연다. 틀린 문제의 진행 칸은 회색이다(주의색이 강조색과 비슷해 지금 문제와 헷갈려서). 질문하기의 대목 찾기는 글자 쌍만 쓰지 않고 조사를 뗀 낱말 줄기와 이웃 낱말 묶음, 드문 낱말 가중, 읽는 장 가중을 쓴다. 질문과 답은 기기에도 서버에도 남기지 않고 그날 그 계정의 메모리에만 두어, 근거 표식으로 읽기 화면에 다녀와도 대화가 이어진다. 서재의 다른 책 소개는 앱 안에 적은 글이고, 룻기 소개는 목업의 제작 메모 대신 읽는 사람에게 맞는 글로 바꿨다. 그림 참고 작품은 style.json의 출처 글에서 주소와 이용 조건을 떼어 자료 출처 화면에 보인다.

## 4. 저장소 구조

```
packages/reader-core/   읽기 계산 모듈과 묶음 타입 (웹·앱 공용, 브라우저·RN API 없음)
app/                    웹 목업 (Vite, 깃허브 페이지). reader-core를 가져다 쓴다
mobile/                 Expo 앱 (expo-router)
server/                 동기화 서버 (Hono, Postgres, jose). 5단계에 질문하기가 더해진다
infra/                  docker-compose.yml(Postgres, 키클락), 키클락 realm 설정, 시험 토큰 스크립트
pipeline/, admin/       지금 그대로. 검색 색인·원어·퀴즈를 만드는 단계가 더해진다
```

- 모두 루트 npm workspaces에 둔다. Expo SDK 57이 React 19.2.3을 고정하므로 웹 목업도 `react`, `react-dom`을 19.2.3으로 맞춰 React가 한 벌만 설치되게 한다(두 벌이면 훅 오류가 난다).
- `reader-core`는 지금 `app/src/reader/`의 순수 모듈과 테스트, `app/src/content/types.ts`(묶음 타입)와 `fillMissing`을 옮긴 것이다. 의존성은 없고, TypeScript 원본을 그대로 내보낸다(웹은 Vite가, 앱은 Metro가 변환한다). `useNarration.ts`처럼 브라우저 API를 쓰는 파일은 옮기지 않는다.
- `mobile/`의 콘텐츠는 `npm run content -w mobile`이 `app/public/content/`(파이프라인 `build`의 결과)에서 복사한다. 그림은 기본 그림 버전만 넣는다(웹의 그림 버전 전환은 시험용이라 앱에는 두지 않는다). 그림·음성 경로를 `require()` 표로 바꾼 `assets.generated.ts`를 함께 만든다. 복사본은 커밋하지 않는다.

## 5. 앱 구조

### 화면 흐름

expo-router 경로로 둔다. 탭 막대는 두지 않는다(읽기 화면이 화면 전체를 쓰는 앱이라서).

| 경로 | 화면 | 목업 |
|---|---|---|
| `/` | 홈: 오늘의 읽기, 이어 읽기, 계획 진도, 바로 가기(연표·지도·인물·가계도·메모·검색·질문하기·서재) | 5 |
| `/read` | 읽기 화면. 목차·연표·여정 지도·카드·설정·밑줄 메모는 그 위에 뜨는 덮개다. 다른 화면은 옮길 절과 열 덮개를 요청으로 보낸다(`mobile/src/navigation.ts`) | 1~4, 9 |
| `/notes`, `/people` | 내 밑줄·메모, 인물 사전 | 9 |
| `/genealogy` | 가계도 | 6 |
| `/search` | 검색 | 8 |
| `/player` | 낭독 플레이어 | 10 |
| `/library` | 서재 | 14 |
| `/ask` | 질문하기 | 13 |
| `/quiz/[chapter]` | 이해 확인 퀴즈 | 12 |
| `/sources` | 자료 출처와 이용 조건(설정 시트, 원어 시트, 서재에서 연다) | 11 |
| `/account` | 로그인, 동기화 상태 | — |

인물·장소 카드, 해설(`?`) 시트, 읽기 설정, 원어 보기, 메모 편집, 공유 카드는 화면 위에 뜨는 시트로 둔다.

### 지도

웹 목업은 Leaflet과 OSM 공용 타일을 쓰는데, 앱 트래픽에 공용 타일을 쓰는 것은 OSM 타일 이용 정책에 어긋난다. 앱은 타일 서버 없이 Natural Earth(퍼블릭 도메인)의 해안선·강·호수 벡터를 근동 지역으로 잘라 묶음 옆에 넣고 `react-native-svg`로 그린다.

설계 승인 때는 MapLibre로 적었으나 SVG로 정했다. 고대 지명 수십 곳만 보이는 지도라 타일 지도 SDK가 필요 없고, SVG는 웹과 기기에서 똑같이 그려져 Expo 웹에서 확인할 수 있으며, 네이티브 지도 SDK의 빌드 문제를 피한다. 확대·이동은 제스처로 SVG 변환 행렬을 바꾸고, 장소 전환 안내의 "날아가기"는 같은 행렬을 애니메이션한다. 지형 음영이 필요하면 Natural Earth 음영 기복 래스터를 같은 투영(등장방형)으로 잘라 밑에 깐다.

### 상태

- 묶음은 앱 시작 때 한 번 읽어 React 컨텍스트로 내려 준다.
- 기기 기록은 `expo-sqlite`에 둔다(6절). 웹에서 확인할 때는 같은 인터페이스를 `localStorage`로 구현한 저장소를 쓴다(`*.web.ts`).
- 읽기 위치와 설정의 형식은 웹 목업(`reader-read-scenes`, `reader-settings`)과 같은 모듈(`reader-core`의 `progress`, `settings`)로 해석한다.

## 6. 기능별 결정 (목업에서 바꾸거나 정한 것)

**1~4. 읽기, 카드, 목차·연표, 설정.** 웹과 같은 동작이다. 글자 크기는 앱 설정(1~5단계)에 기기의 시스템 글자 크기를 곱한다. 장면 사이는 그림을 좌우로 밀어 넘긴다.

**5. 읽기 계획과 진도(홈).** 계획은 "하루 한 장", "하루 장면 N개(1~5)", "자유" 셋. 완독 예정일과 "N일째"는 계획 시작일과 읽은 장면으로 계산한다. 낭독 예상 시간은 음성 파일 길이의 합으로 보여 준다(묶음 빌드 때 mp3 길이를 재 `audioMs`로 넣는다). 목업의 "오프라인용으로 1~5장 받아 둠 · 38 MB" 줄은 뺀다. 묶음이 처음부터 앱 안에 있어 받을 것이 없다.

**6. 가계도.** 설정집 인물의 `relations` 중 부모·자녀 관계로 그린다. 목업은 4~5장으로 고정했지만, 앱은 읽은 장까지만 펼치고 아직 읽지 않은 장에 처음 나오는 인물은 가린다(줄거리를 미리 보여 주지 않으려고). 같은 이름(에녹, 라멕)은 아버지로 구분해 두 줄기에 따로 둔다. 연도는 인물의 `years`를 쓰고, 목업의 주의 문구(번역·사본에 따라 수치가 다름)를 아래에 둔다.

**7. 장면 카드 공유.** 장면 그림, 고른 절 하나, "창세기 5장 24절 · 개역한글", 장면 제목, 앱 이름을 정사각 카드로 기기에서 그려(`react-native-view-shot`) 시스템 공유창(`expo-sharing`)에 넘긴다. 서버를 거치지 않는다. 웹에서는 Web Share API, 없으면 이미지를 새 창에 연다.

**8. 검색.** 앱이 묶음을 그대로 훑어 오프라인으로 찾는다(색인 없이도 충분히 빠르다). 대상은 본문, 낱말 풀이, 설정집(인물·장소·시대·물건), 장면 제목·해설. 띄어쓰기를 무시하고, 한글 초성만 입력해도 찾는다(예: "ㄱㅇ" → 가인). 목업의 "비슷한 말" 결과는 뺀다(의미 검색은 임베딩이 필요해 이번 범위 밖). 최근 검색어는 기기에만 둔다. 설정집 물건을 검색에 쓰려고 묶음에 승인된 `things`를 더한다(키 추가라 `schemaVersion`은 1 그대로).

**9. 밑줄·메모·즐겨찾기.** 단위는 절이다. 글자 단위 범위는 본문이나 띄어쓰기가 고쳐지면 위치가 어긋나서 쓰지 않는다. 밑줄 색은 노랑·초록·파랑 셋, 메모는 절마다 하나, 즐겨찾기는 절에 별표. 본문의 절을 길게 눌러 연다. 목업 문구대로 "이 기기에 저장돼요. 로그인하면 다른 기기에서도 볼 수 있어요"를 둔다.

**10. 낭독 플레이어.** 파이프라인 `tts` 단계로 미리 만든 절 단위 mp3를 `expo-audio`로 이어 재생한다. 기기 음성 합성(TTS)은 iOS 백그라운드에서 끊겨 쓰지 않는다. 잠금 화면·이어폰 버튼 조작, 속도(0.8, 1.0, 1.2), 자막 켬/끔, 잠자기 타이머(15·30·60분, 장면 끝에서 멈춤), "다음에 들을 것"(다음 장면들)을 둔다. 웹 목업의 낭독은 지금처럼 브라우저에서 같은 mp3를 재생한다.

**11. 원어와 출처.** 히브리어 본문과 형태 정보는 OSHB(Open Scriptures Hebrew Bible, CC BY 4.0), 사전 번호와 영어 뜻은 스트롱 히브리어 사전(퍼블릭 도메인)을 쓴다. 한국어 절 낱말과 히브리어 낱말을 짝짓지는 않는다(자동 정렬은 틀리기 쉽다). 대신 절마다 히브리어 낱말을 순서대로 보이고, 낱말마다 음역, 품사, 스트롱 번호, 한국어 뜻을 붙인다. 한국어 뜻은 파이프라인이 초안을 쓰고 관리 도구 검수 대기열에서 승인한 것만 묶음에 들어간다. 목업의 "[확인 날짜]", "[출처 1]" 자리 표시는 실제 데이터로 바꾼다. 역사 배경은 지금 묶음의 `history[].sources`를 그대로 보이고, 확인 날짜 줄은 뺀다(웹 검색 확인 단계 `review-facts`가 아직 없다). 앱 정보 화면에 쓰는 자료의 출처와 이용 조건(개역한글, OSHB, 스트롱 사전, Natural Earth, 그림 참고 작품)을 모아 둔다.

**12. 이해 확인 퀴즈.** 장마다 4지선다 다섯 문제. 파이프라인 `quiz` 단계가 본문과 검수된 해설에서만 문제를 쓰고, 검수 모델이 정답 근거 절을 확인한 뒤, 사람이 관리 도구에서 승인한 문제만 묶음에 들어간다. 점수는 남기지 않는다(목업 문구 "틀려도 점수는 남지 않아요"). 그 장의 퀴즈를 끝까지 풀었다는 표시만 기기에 남긴다.

**13. 질문하기.** 로그인한 사람만 쓴다. 서버가 승인된 묶음(본문, 해설, 역사 배경, 설정집) 안에서 관련 대목을 찾고, LLM이 그 대목만 근거로 한국어로 답한다. 답에는 근거 표식(본문 4:15, 해설 · 장면 제목, 설정집 · 이름)을 붙이고, 누르면 그 자리로 간다. 근거가 없으면 "자료에 없어요"로 답한다. 한 사람당 하루 20번으로 제한한다. LLM 키는 서버에만 있다.

**14. 서재.** 책마다 묶음 하나. 지금은 창세기만 열린다. 출애굽기·룻기·요나·마가복음은 "만드는 중", "예정"으로 소개만 보인다. 창세기 카드의 장·장면 수는 묶음에서 센다(목업의 "장면 38개"처럼 손으로 적지 않는다). "제작 과정 보기"는 앱 안의 짧은 설명 시트로 둔다.

**15. 홈 화면 위젯.** "오늘의 장면"(다음에 읽을 장면의 그림, 제목, 절 범위, N일째)과 "이어 읽기" 버튼. 안드로이드는 `react-native-android-widget`, iOS는 WidgetKit 확장(`@bacons/apple-targets`)으로 만든다. 앱이 위젯용 데이터를 공유 저장소(App Group, SharedPreferences)에 써 두고 위젯이 읽는다.

## 7. 기기 저장과 동기화

### 기기 저장소 (`expo-sqlite`)

| 표 | 내용 |
|---|---|
| `readScenes` | 읽은 장면 id, 읽은 날(연속 읽기와 계획이 쓴다) |
| `position` | 마지막 읽기 위치(장, 장면, 절) |
| `plan` | 계획 종류, 하루 장면 수 |
| `marks` | 절 기록: `kind`(highlight, note, bookmark), 장·절, 색, 메모 글 |
| `quizDone` | 끝까지 푼 장 |
| `settings` | 읽기 설정(웹과 같은 형식). 기기마다 달라 동기화하지 않고 kv에 둔다 |
| `recent_searches` | 최근 검색어 (동기화하지 않음) |

동기화하는 기록(`readScenes`, `position`, `plan`, `marks`, `quizDone`)은 모두 `records` 표 하나에 (컬렉션, id) 줄로 둔다(웹 미리 보기는 localStorage). 줄은 `updatedAt`(기기 시각, ms), `deletedAt`(지움 표시), 아직 안 올렸는지를 가진다. 고친 시각은 그 줄의 앞 시각보다 늘 뒤로 두어, 기기 시계가 늦어도 새로 고친 것이 이긴다. 지울 때는 줄을 없애지 않고 `deletedAt`을 적고 내용은 비운다.

### 동기화

- `POST /sync` 한 번으로 밀어넣기와 당겨오기를 함께 한다. 요청: `{ since: 서버 순번, changes: 줄[] }`(한 번에 500줄까지, 앱이 나눠 올린다). 응답: `{ changes: since 이후 바뀐 줄[], now: 다음에 보낼 순번, more: 더 받을 것이 있는지 }`.
- 같은 줄이 양쪽에서 바뀌면 `updatedAt`이 늦은 쪽이 이긴다. 당겨올 위치는 서버가 매기는 단조 증가 순번으로 정해 기기 시계가 틀려도 빠뜨리지 않는다. 서버는 같은 사용자의 동기화를 사용자별 잠금으로 차례로 처리해, 받아 간 순번보다 앞 순번이 늦게 쓰이는 일이 없다.
- 받은 줄을 합치는 규칙(`mergeRemote`, `applySyncResponse`)은 `reader-core/src/sync.ts`의 순수 함수다. 올린 뒤 다시 고치지 않은 줄만 올린 것으로 표시하고, 받은 줄은 한 번에 쓴다(SQLite 트랜잭션 하나).
- 앱이 앞으로 올 때, 기록을 바꾸고 3초 뒤, 로그인 직후에 동기화한다. 실패하면 다음 기회에 다시 한다. 로그인 전 기록(주인 없음)은 첫 동기화 때 그 계정으로 올라간다. 로그인이 풀린 뒤 다른 계정으로 들어오면 앞 계정의 기록은 올리지 않고 비운다.
- 로그아웃하면 기기 기록을 지운다(다시 로그인하면 받아 온다). 못 올린 기록이 있으면 먼저 올려 보고, 못 올렸으면 한 번 더 묻는다.

## 8. 로그인과 서버

### 키클락

- 개발용은 `infra/docker-compose.yml`의 키클락(`start-dev`)이고, realm 설정 파일 `infra/keycloak/chansu-bible-realm.json`을 시작할 때 읽어 들인다.
- realm `chansu-bible`, 공개 클라이언트 `chansu-bible-app`(Authorization Code + PKCE S256, `offline_access`). 리디렉트 주소는 앱 `chansubible://auth`, Expo Go `exp://`, Expo 웹 `http://localhost:8081/*`. 회원 가입 켬, 한국어 화면. 로그인 창은 늘 로그인 양식을 보인다(`prompt=login`).
- 개발용 시험 클라이언트 `chansu-bible-test`(비밀번호로 토큰 받기)와 `infra/dev-token.mjs`로 서버를 손으로 시험한다. 운영 realm에는 만들지 않는다.
- 시험용 계정은 realm 설정 파일에만 적는다(개발용 realm이라서). 운영 realm은 나중에 따로 만든다.
- 앱은 `expo-auth-session`으로 로그인한다. 앱은 앱 안 브라우저로 로그인 창을 열고, Expo 웹은 같은 창에서 갔다가 `/auth`로 돌아온다(PKCE 검증값은 그동안 sessionStorage에 둔다). 갱신 토큰은 `expo-secure-store`(웹은 `sessionStorage`)에, 액세스 토큰은 메모리에 둔다. 로그아웃하면 갱신 토큰을 키클락에서 무른다. 주소는 `EXPO_PUBLIC_AUTH_ISSUER`, `EXPO_PUBLIC_API_URL`로 바꾼다(안드로이드 에뮬레이터는 `10.0.2.2`, 실제 폰은 컴퓨터의 내부망 주소).

### 서버 (`server/`)

- Hono(Node), Postgres 17(`pg`, SQL을 직접 쓴다). 개발 포트 8790, `127.0.0.1`에만 묶는다(관리 도구 8787과 겹치지 않게). 개발 중에는 호스트에서 `npm run server`(tsx watch)로 돌리고, 도커에는 Postgres와 키클락만 둔다.
- 모든 요청은 `Authorization: Bearer`의 토큰을 키클락 JWKS로 검증한다(`jose`). `iss`, `azp`, 만료를 본다. 사용자는 토큰의 `sub`로 구분한다.
- 경로: `GET /health`, `GET /me`, `POST /sync`, `POST /ask`(5단계).
- 표: `records`(사용자 `sub`, 컬렉션, id가 키. 내용은 JSONB, `seq`는 순번 `record_seq`에서 받는다). 5단계에 `ask_usage`(사용자·날짜별 횟수)가 더해진다. 읽기 설정은 기기마다 달라 서버에 두지 않는다.
- `POST /ask`는 서버가 시작할 때 묶음(`app/public/content/genesis.json`)을 읽어 두고, 대목 찾기(낱말 겹침 점수)로 상위 대목 몇 개를 고른 뒤 LLM에 보낸다. OpenAI 키는 서버의 `.env`에만 둔다.

## 9. 검증과 빌드 환경

- `reader-core`, `server`, `pipeline`: vitest. 서버 테스트는 PGlite(메모리 Postgres)로 돌려 도커 없이 된다. 키클락 토큰 검증은 테스트용 키 쌍으로 만든 JWKS로 시험하고, 실제 키클락·Postgres는 `infra/dev-token.mjs`로 손으로 확인한다.
- `mobile`: 계산·저장·동기화 규칙은 `reader-core`로 옮겨 vitest로 시험하고, 앱은 형 검사를 한다. 화면은 Expo 웹(`npm run web -w mobile`)을 브라우저 창에서 열어 확인한다.
- 네이티브 빌드: 이 컴퓨터에는 Android SDK가 없다(JDK 17·21은 있다). 4단계(백그라운드 낭독, 위젯)는 기기 빌드가 있어야 확인되므로, 그 전에 Android SDK를 설치할지, Expo 클라우드 빌드(EAS) 계정을 쓸지 사용자가 정한다. iOS 빌드는 맥 또는 EAS가 필요하다. Windows에서 안드로이드 새 아키텍처를 빌드할 때 경로 길이 260자 제한에 걸릴 수 있다.

| `verse.audioMs` | 2 | 절 낭독 길이(ms). 음성이 없으면 null |
| `scene.audio`, `scene.audioMs` | 4 | 장면 낭독(장면에 든 절 낭독을 이은 MP3, `content/audio/scenes/<장면 id>.mp3`)과 길이. 앱은 이것을 재생하고 절 위치는 절의 `audioMs`로 찾는다 |
| `chapter.original` | 5 | 절별 히브리어 낱말(본문, 음역, 품사, 스트롱 번호, 승인된 한국어 뜻) |
| `chapter.quiz` | 5 | 승인된 퀴즈 문제(질문, 보기 넷, 정답, 해설, 근거 절) |
| `sources` | 5 | 자료 출처와 이용 조건 목록 |

## 11. 위험과 대응

- **React 두 벌 설치.** 버전을 맞춰도 생기면 Metro 설정에서 `react`를 루트 한 곳으로 고정한다.
- **네이티브 빌드 없이 만든 4단계 코드.** 기기에서 처음 돌릴 때 고칠 것이 나온다. 4단계 완료는 기기 확인 뒤에만 표시한다.
- **원어 한국어 뜻과 퀴즈의 LLM 비용.** 창세기 1~10장 히브리어 낱말은 표제어 기준 수백 개라 초안 비용은 몇 달러 안쪽이다. 퀴즈는 장마다 호출 두 번(쓰기, 검수)이다.
- **질문하기의 틀린 답.** 근거 대목 밖의 내용은 쓰지 않게 지시하고, 근거 표식이 없는 문장이 있으면 서버가 답을 버리고 "자료에 없어요"로 바꾼다. 화면에 "AI가 쓴 글이라 틀릴 수 있어요"를 둔다.
